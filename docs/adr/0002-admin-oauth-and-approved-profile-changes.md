# Use administrator OAuth and approved profile changes

Ordinary-user OAuth consent does not authorize Directory profile writes, even to the user's own account. For this small nonprofit, users submit verified contact email and phone changes for approval; the application executes approved changes and administrative operations using the acting administrator's OAuth credentials. Google therefore enforces that administrator's privileges and resource restrictions, without a shared stronger account or a parallel application role model.

Prefer this workflow over domain-wide delegation: Google's Directory user write scope is not limited to contact fields, and delegation scopes do not restrict which account a service account may impersonate. The trade-off is that contact changes wait for an authorized administrator instead of taking effect immediately. Domain-wide delegation can be reconsidered if that approval delay becomes unacceptable.

Request `admin.directory.user` for user management and `admin.directory.group` for group and membership management; add read-only role inspection only if required for the interface. Restrict profile change requests to contact email and phone, preserve unrelated Directory entries, and keep Workspace email, account recovery fields, and security settings outside that workflow. A new contact email must be verified before it can be approved. Do not retry denied operations using stronger credentials.

Send verification, outcome, and administrator notification emails through a dedicated Workspace mailbox with a separate offline OAuth grant limited to `gmail.send`. Notify a configured Google Group when a verified signup or profile change request is submitted, including a review-queue link and minimal personal information. The notification group's membership determines delivery only, never approval authority; configure it to accept mail from the sender.

Assume administrator-managed Directory/contact sharing is enabled and managed users are visible in the Directory. Read the signed-in user's own profile with their OAuth grant containing `admin.directory.user.readonly`, explicitly using `viewType=domain_public`. Resolve the target from the authenticated identity and return only that user's permitted shared fields. Omitted contact fields are unavailable, not evidence that the stored value is empty. Keep credentials server-side; no shared reader account, delegated Users Read role, or private/admin-view fallback is required. Administrative reads and approved writes still use the acting administrator's grant.

Require a successful current own-profile lookup for protected access; unavailable/hidden/deleted profiles or rejected credentials deny access with an explicit unavailable or reconnection outcome. This is a visibility/access check, not an administrator-only `suspended` status check. Verify suspended/deleted-account behavior with existing sessions in the live tenant; access denial depends on Google's credential and Directory propagation and must not be described as instantaneous suspension detection.
